## Google's actual data model (Dataplex Universal Catalog, née Data Catalog)

Requested follow-up: read the real Google standard behind that repo, not just
the repo's own docs, and check whether more of it is worth borrowing.
Confirmed with Google's own docs (sources at bottom) — this is the model
`mdcode`/OKF's own author says it deliberately mirrors ("a YAML representation
that largely aligns with the Entry/EntryLink+Aspect data model in Knowledge
Catalog", `mdcode/docs/concept.md:20-21`). So OKF v0.2 isn't a separate thing
from Google's model — it's Google's model, minus the parts that need a live
GCP service. That reframes item 3/4 above: adopting `generated`/`verified`/
`sources[]` **is** adopting Google's Aspect pattern, just file-based.

**The model, plain:**

| Google concept | Definition (verbatim) | Our nearest equivalent |
|---|---|---|
| `EntryGroup` | "a regional container for entries and entry links that acts as the administrative and security boundary" | `knowledge/bundle/splitter_des_ewigen/` (we only have one — fine, we're single-campaign, single-tenant) |
| `EntryType` | "a governance template... establishing the required aspect types that must be attached to an entry of that type" | our typed IDs (`CHAR_`/`NPC_`/`LOC_`/...) — but we don't enforce required fields per type today |
| `AspectType` | "a reusable schema template that defines the fields, data types, and validation rules for an aspect" | nothing dedicated — we bolt ad hoc frontmatter keys (`status`, future `sources`/`verified`) straight onto the concept instead of a separately-schema'd block |
| `Aspect` | "a set of related metadata fields that conforms to an aspect type... attached to an entry, an entry path, or an entry link" | closest existing thing is the "# Belege" body section — unstructured, not schema-validated |
| `EntryLink` / `EntryLinkType` | typed relationship between two entries; built-ins `synonym` (bi-directional), `related`, `definition` (business term → column, directional), `schema-join`; aspects can attach to a link to describe the relationship itself | our cross-links (`links.py`) are untyped markdown wikilinks resolved to a concept id — no relationship semantics (member_of vs. enemy_of vs. located_in are all just "a link"), nothing attachable to the edge |
| Business Glossary (`Glossary` → `Category` → `Term`, ≤3 category levels, `synonym`/`related` term links, `definition` link to physical columns, per-term `Contacts` steward field) | campaign-vocabulary equivalent would be canonical in-world terms (deity titles, faction ranks, "Kanon-Entscheidung" itself) — we don't have this layer; terms currently just live as prose inside whichever concept first defines them |

Google doesn't document AspectType schema versioning/migration either — so we're
not behind the state of the art there, it's an open problem for them too.

**What's actually worth borrowing, ranked:**

1. **Typed entry links > untyped wikilinks.** This is the single highest-value
   idea from the research. Right now two characters being allies and two
   characters being enemies look identical in the bundle graph — just a
   markdown link. Adding a small closed vocabulary of relationship types
   (`member_of`, `allied_with`, `enemy_of`, `located_in`, `rules_over`, ...)
   the way Google's built-in `EntryLinkType`s do, and optionally letting a
   relationship carry its own small aspect (e.g. `since`/`until` session,
   confidence) mirrors what `ROLL_` rows already do with `confidence` — same
   pattern, extended to relationships. This is a **new capability**, not a
   spec-compliance gap — evaluate it as its own design question, not a
   sub-task of the v0.2 upgrade.
2. **AspectType-style validation per EntryType** — i.e. formalize which
   frontmatter fields are required/optional per entity type (`CHAR_` always
   needs `aliases`? `FACTION_` always needs a `rules_over`/`member_of` link?)
   and check it as part of `services/kb`'s existing validation pass
   (`validate.py`). Cheap, catches malformed emit output, no new file format.
3. **Business glossary layer — skip for now.** Interesting parallel (in-world
   canonical terms) but no existing pain point motivates it (no reports of
   term ambiguity), and Google's own version tops out at "a Contacts field,
   no draft/approved lifecycle" — i.e. even their real product doesn't do
   much more than we could hand-roll in an hour if we ever needed it. Revisit
   only if term-consistency actually becomes a problem in `reports/`.

None of this needs a live GCP resource or the `mdcode` sync tooling — it's
"steal the modeling idea, implement it as more OKF frontmatter," consistent
with the "Ruled out" section above.
